# USER*-{ID,LN,OI}.idx — Index Files

Each `USERN.tbl` is accompanied by three index files. They are **derived
100% deterministically from the table contents** — the build algorithm
below reproduced all 48 reference index files byte-for-byte, from 828-byte
single-node files up to 648 kB production B-trees.

Reference implementation: `build_idx()` in
`Euronav5 avkodning/analysis/euronav5.py`.

All integers little-endian.

## Key per index type

| File | Key | Value |
|------|-----|-------|
| `-ID.idx` | USEROBJECTID (signed) | row ID |
| `-LN.idx` | LONGITUDE (microdegrees, signed) | row ID |
| `-OI.idx` | ID (row number) | row ID |

## File layout

```
[60-byte header][K × 768-byte nodes]      fileSize = 60 + K × 768
```

Common sizes: 828 bytes = header + 1 node (up to 63 records — covers all
ten test sets); production trees: hundreds of nodes.

### Header (60 bytes)

| Offset | Type | Value |
|--------|------|-------|
| 0x00 | u16 | 3 |
| 0x02 | u16 | 3 |
| 0x04 | i32 | file offset of root node (60 when single-node) |
| 0x08 | i32 | 0 |
| 0x0c | i32 | −1 |
| 0x10 | i32 | −1 |
| 0x14 | i32 | maximum key |
| 0x18 | u32 | 0x80000000 |
| 0x1c | u32 | 0x80000000 |
| 0x20 | i32 | row ID of the max-key entry (largest row ID among ties) |
| 0x24 | i32 | same as 0x20 |
| 0x28 | i32 | minimum key |
| 0x2c | u32 | 0x80000000 |
| 0x30 | u32 | 0x80000000 |
| 0x34 | i32 | row ID of the min-key entry (smallest row ID among ties) |
| 0x38 | i32 | same as 0x34 |

(The old docs had min/max at 0x14/0x28 reversed: 0x14 is the **max**.)

### Node (768 bytes)

```
+0x000  i32        nkeys (0–63)
+0x004  i32        0
+0x008  64 × i32   child node FILE OFFSETS; -1 = none (leaf: all -1)
+0x108  63 × (i32 key, i32 rowId)   entries, sorted; duplicates by rowId
                   unused entry slots are zero-filled
```

## Build algorithm (byte-exact)

A B-tree with max 63 keys per node, built by **inserting the table rows in
row-ID order (1…N)**:

1. Start with a single empty leaf (node 0).
2. To insert `(key, rowId)`: descend from the root; at each node go to the
   child after the last entry whose key ≤ new key (duplicates go right).
   Insert into the leaf at that position.
3. If a node now holds 64 entries, split it: entries 0–30 stay, entry 31
   moves up to the parent, entries 32–63 move to a **new right sibling**.
   Splits cascade upward; if the root splits, a new root is created.
4. **Allocation order** (= order of the 768-byte nodes in the file): new
   nodes are appended in creation order, and in a cascade the child's
   sibling is created first, then the parent's sibling, then (if needed)
   the new root. The header's root offset points at the final root.

### Quirk: stale pointer in child slot 63

When an *internal* node splits, the planner clears the vacated child slots
to −1 — except slot 63, which keeps the pre-split pointer. This off-by-one
is reproduced in `euronav5.py` and is required for byte-identity with
planner output. Entry (pair) slots are properly zero-filled.

## Single-node form (≤ 63 records)

Everything iOS realistically exports fits one node, so the file is simply:

```
header (60 B, root offset = 60)
node:  nkeys = recordCount, 0, 64 × -1,
       sorted (key,rowId) pairs, zero padding to 63 slots
```

## Empty-table variant

`full_db` contains 60-byte index files (header only, root offset −1,
max = INT_MIN, min = INT_MAX) next to empty tables. These are old relics
(2017–2022 timestamps) and were not regenerated by the current planner;
none of the test sets contain empty layers. See VERIFICATION.md open
questions before relying on this variant.
